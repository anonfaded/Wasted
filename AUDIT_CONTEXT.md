## What this project is

Wasted (Modded) is an Android app (minSdk 24) with Device Admin, local triggers, P2P, and an optional
Remote Management layer:

- Remote Lock Timer / USB Trigger sync, Reset Timer, Force Reset.
- Device registration, status/timer reporting, Debug Mode status.
- Optional notifications, offline-safe behavior.
- A lightweight, portable, self-hosted dashboard.

**Deployment model:** every user creates their **own Supabase project** and hosts their **own
dashboard copy**. There is no shared backend or central dashboard URL. The app's setup wizard
collects the project URL + publishable key, provides the SQL and Auth checklist, and generates a
single-file dashboard saved via Android SAF. Supabase Cloud is the backend; Docker is local-dev only.

## Latest UI/auth changes (verify these)

- Sign In and Create Account are separate one-at-a-time forms, not mixed fields.
- Emails are filtered before insertion: lowercase, no whitespace, restricted practical email
  character set; HTML validation and Supabase validation still apply. Passwords are not trimmed.
- Password fields have an eye toggle; dynamic values are rendered with `textContent`.
- Confirm email is recommended/on; after signup the dashboard switches to Sign In and tells the user
  to confirm. `emailRedirectTo` uses the dashboard URL; Auth Site URL must be set to that URL.
- Account name is only a dashboard display label. Device names are separate, editable in the app
  (prefilled with `Build.MODEL`) and renameable in the dashboard.
- Dashboard device cards have Rename/Revoke; all state-changing actions (settings, token creation,
  Debug Mode, Reset Timer, Force Reset, revoke) require confirmation. Revoke does not wipe; the
  device must run Reset enrollment before re-pairing.
- Setup guide has project/SQL/Auth/URL/Netlify links; Netlify updates must replace `index.html` in

- `web/config.js` and `web/assets/app.js` are generated by `npm run dev` for source testing and are
  gitignored; production is `web/dist/index.html` or the app-generated `index.html`, plus the

## Third-audit fixes (verify in audit 4)

- **P2P High:** peer leaf certificates are pinned during pairing; client certificates are required;
  handshake device IDs and every message are bound to the verified TLS peer; paired certificate
  changes are rejected. The P2P Room database is SQLCipher-encrypted; legacy plaintext rows are
  imported as unpaired and require re-pairing. Pairing PINs use `SecureRandom`, one-time consumption,
  and attempt lockout. Runtime spoof/replay/two-device tests remain open.
- **Verifier negative proof:** `supabase/tests/verify_negative.sh` runs the real `verify.sql` after
  extra-policy, mismatched-predicate, and PUBLIC-default drift; `remote_verify_drift_test.sql`
  remains as a quick static supplement.
- **P2P privacy:** production logs no longer include peer names, IPs/ports, device/message IDs, or
  command identifiers.
- **Email low finding:** duplicate `@` is deduplicated for all insertion/paste paths; `normalizeEmail`
  is covered by web tests (25/25).
- **Docs:** notifications default ON, 25 web tests, cumulative update wording, and P2P encryption
  are aligned.

## Key decisions (scrutinize these)

1. **Per-user self-hosting** (client requirement): each user runs their own Supabase + dashboard.
2. **App-generated dashboard, no runtime connect form:** app injects URL + publishable key into a
   bundled template and exports via SAF. No file editing. A shared/central dashboard URL and
   localStorage-based runtime config were rejected.
3. **Setup = one `setup.sql` in SQL Editor + Auth guidance** (enable anonymous sign-ins, keep
   Confirm email enabled, set Auth Site URL). No CLI/Docker for end users; Docker is not an
   end-user deployment path.
4. **Migrations:** flat immutable history (`supabase/migrations/`) because Supabase CLI requires it;
   `releases.json` maps app version → schema version → cumulative migrations; per-release folders
   (`supabase/releases/<version>/`) contain generated `setup.sql`, cumulative update bundles,
   `verify.sql`, checksums, and generated instructions. **No automatic update check**; release notes
   name the bundle.
5. **Publishable key is public by design; secret/service-role keys never ship.** The dashboard
   contains only URL + publishable key.
6. **Debug Mode:** default ON, encrypted, re-read inside `ResetExecutor`; remote Force Reset blocked
   while ON; remote per-device toggle requires owner action and supersedes pending Force Resets.
7. **Explicit Create Account** instead of the spec's “auto-create if feasible” wording (safer; flagged
   as a deviation for client confirmation).
8. Notifications only for meaningful events (no heartbeat-success spam; manual sync success only);
   notifications default ON.
9. Views/ViewBinding (no Compose rewrite), minSdk 24 retained.
10. **Single-owner guard:** one dashboard account per project; extra Auth users are inert.

## Specific claims to verify (don't take the docs on faith)

- RLS is enabled/forced; `anon` has no table access; `authenticated` is select-only; writes only via
  SECURITY DEFINER RPCs; default privileges hardened.
- P2P TLS pins the peer leaf certificate, requires client certificates, and binds handshake/message
  IDs to the verified peer; the P2P Room database is SQLCipher-encrypted; legacy rows require
  re-pairing. Pairing PINs use `SecureRandom` with one-time consumption and attempt lockout.
- Owner/device isolation, revocation behavior, enrollment token hashing/single-use/10-minute expiry,
  idempotency keys, command/action consistency trigger.
- Force Reset ordering and terminal allowlists; interrupted `executing` rows never replay
  destructively; Debug Mode re-read at every boundary.
- `set_device_debug_mode` targets one device; OFF expires pending Force Resets
  (`superseded_by_debug_off`).
- Settings revisions apply only when newer; status fields and TTLs match the docs.
- Generated SQL covers every migration exactly once, per-release bundles are cumulative from each
  earlier release and checksummed, and Gradle regenerates the assets before asset merging.
- The dashboard uses `textContent` (no `innerHTML`), filters email input before insertion,
  validates keys/URLs, rejects secret keys, and confirms every state-changing action.
- Confirm email verifies ownership only; public signups remain open, but the single-owner guard
  prevents a second usable dashboard account. Disabling email signups or host access control is
  optional additional hardening (residual abuse risk, not cross-account access).
- Device revoke hides the device and stops commands immediately; the anonymous identity is cleaned
  up after 30 days, but the device row remains. Re-pairing requires Reset enrollment on the device.
