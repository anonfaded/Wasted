# Hosting the dashboard

The dashboard is **generated by the app** as one self-contained HTML file. It contains only the
project URL and publishable key and talks directly to Supabase over HTTPS/WSS. There is no dashboard
server, database credential, or CDN dependency.

## Steps (Netlify Drop — simplest)

1. In the app: **Remote Management → Open setup wizard** → enter project URL + publishable key.
2. Tap **Generate dashboard file** and save it as `index.html`. The app suggests this name because
   Netlify Drop requires an `index.html` home page; a differently named file shows “page not found.”
3. Open <https://app.netlify.com/drop> and drag the file in.
4. Netlify gives you a temporary HTTPS URL (`https://…netlify.app`). Until you claim it, the site is
   password-protected and **expires after 1 hour**. Click **Claim this site**, sign in or sign up,
   then copy the final HTTPS URL.
5. Open the URL, create your account, then enter it in the app and enable Remote Management.

If the temporary site expires before you claim it, upload the file again and use the new URL. If you
later move to a different host or URL, update **Remote Management → 2. Dashboard URL**, save, and test
again; an old URL stops working, but the device enrollment remains valid.

**HTTP 401 after a dashboard test** usually means the Netlify Drop site is still password-protected
or unclaimed. Claim it, wait for the claim to finish, then test the final URL again.

## Alternatives

- **Cloudflare Pages** — Create project → direct upload → drop the file.
- **GitHub Pages** — publish from a `docs/` folder or an Actions workflow.
- **Vercel** — `vercel deploy --prod` from a folder containing only `index.html`.
- Any HTTPS static host (S3 + CloudFront, nginx, Caddy, …).

No CORS setup is needed (password sign-in only). If Confirm email is enabled, set the Supabase Auth
**Site URL/redirect URL** to the dashboard URL. HTTPS is required.

## Updating the dashboard

Regenerate the file in the app and drag the new `index.html` to the **same host and site**. On
Netlify Drop, open the claimed site and replace/redeploy the file there — do **not** create a new
site, because that changes the URL and you would have to update Remote Management. Keep the previous
file if you want a rollback path. If the publishable key rotates, regenerate the file and update the
app's saved key.

## Backups and restore

Hosting has no data to back up: the dashboard is stateless and the database lives in Supabase. Back
up Supabase before schema updates; see [updates.md](./updates.md).

## Anti-framing and response headers

A meta CSP cannot set `frame-ancestors`, so the single HTML file alone cannot prevent framing.
Production hosting must send:

- `Content-Security-Policy: …; frame-ancestors 'none'`
- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`

The repository provides `web/_headers` for hosts that support `_headers` files (Netlify, Cloudflare
Pages): deploy a folder containing `index.html` and `_headers`, or configure the equivalent headers
in the host. The page also includes a frame-busting fallback, but it is defense-in-depth only.

## CSP and custom domains

The page ships a restrictive CSP meta policy allowing only `*.supabase.co` connections plus inline
scripts/styles, and `no-referrer`. If you use a custom/self-hosted Supabase domain, adjust the CSP
and rebuild. For strict deployments, serve the config externally and use response-header CSP hashes
plus `frame-ancestors 'none'`.

## Why not environment variables?

This is a static page: any value the browser needs is delivered to the browser. Netlify-style env
vars only help build steps/functions; they do not hide values from visitors. The publishable key is
public by design, and the secret key must never be in the page.
