# Hosting the dashboard

The dashboard is **generated by the app** as a small static package: one self-contained HTML file
plus the web app manifest, service worker, and icons. It contains only the project URL and
publishable key and talks directly to Supabase over HTTPS/WSS. There is no dashboard server,
database credential, or CDN dependency.

## Steps (Netlify project — supported)

1. In the app: **Remote Management → Open setup wizard** → enter project URL + publishable key.
2. Tap **Save dashboard ZIP**. It contains `index.html`, `manifest.webmanifest`, `sw.js`,
   `icons/`, and `_headers`; deploy all of it. It provides installable PWA support and the offline
   app shell. Netlify requires an `index.html` home page; a differently named file shows “page not
   found.”
3. Sign in to <https://app.netlify.com/> and choose **Add new project → Deploy manually**. Upload
   the ZIP. This creates one project in your team.
4. Confirm the project appears, make it public if it is private by default, and copy its final HTTPS
   URL.
5. Open the URL, create your account, then enter it in the app and enable Remote Management.

To update later, open that same project → **Deploys** and drop the new ZIP there. Do not create another
project; that changes the URL. If you cannot find the project, check the Netlify team selector.

If you later move to a different host or URL, update **Remote Management → 2. Dashboard URL**, save,
and test again; an old URL stops working, but the device enrollment remains valid.

**HTTP 401/403 after a dashboard test** usually means the Netlify project is private or
password-protected. Make it public (or disable password protection), then test again.

No CORS setup is needed (password sign-in only). Signup is direct and does not send email, so no
Auth Site URL or Redirect URL is required for owner signup. HTTPS is still required.

## Updating the dashboard

Regenerate the package in the app, open the **same Netlify project → project menu → Deploys**, use
the deploy area, and upload the new ZIP. Do **not** create another project, because that changes the
URL and you would have to update Remote Management. Keep the previous deploy if you want a rollback
path. If the publishable key rotates, regenerate the package and update the app's saved key.

## Backups and restore

Hosting has no data to back up: the dashboard is stateless and the database lives in Supabase. Back
up Supabase before schema updates; see [updates.md](./updates.md).

## Anti-framing and response headers

A meta CSP cannot set `frame-ancestors`, so the host must send the framing policy.
Production hosting must send:

- `Content-Security-Policy: …; frame-ancestors 'none'`
- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`

The repository provides `web/_headers` for Netlify: deploy the package containing `index.html`,
`manifest.webmanifest`, `sw.js`, `icons/`, and `_headers`. The page also includes a frame-busting
fallback, but it is defense-in-depth only.

## CSP and custom domains

The page ships a restrictive CSP meta policy allowing only `*.supabase.co` connections plus inline
scripts/styles, and `no-referrer`. If you use a custom/self-hosted Supabase domain, adjust the CSP
and rebuild. For strict deployments, serve the config externally and use response-header CSP hashes
plus `frame-ancestors 'none'`.

## Source/local builds

The app-generated ZIP is the normal path. If you are building the dashboard from source, copy
`.env.example` to `.env` at the repository root and set:

```dotenv
SUPABASE_URL=https://YOUR-PROJECT.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_KEY
DASHBOARD_URL=http://localhost:5173/
```

`pnpm dev` in `web/` loads those values through Vite. `pnpm build` writes them into
`web/dist/index.html` and copies `_headers`; deploy the whole `web/dist` directory.
The remaining `.env.example` entries are optional local reference for Supabase CLI,
database, and account work; the app and dashboard do not read them, and they can stay
empty. Never put the secret/service-role key, database password, or account password in
the three public values.

For a manual Netlify CLI deploy, no `netlify.toml` is needed:

```bash
cd web && pnpm build
netlify deploy --prod --dir=dist
```

For a Git-connected Netlify build, set the same three public variables in the site’s
environment settings and configure the build command as `pnpm build` with base `web`
and publish directory `dist`; that is the only case where a `netlify.toml` is useful.

## Why secrets cannot be hidden in the page

For a deployed static page, any value the browser needs is delivered to the browser.
Netlify-style env vars only help build steps/functions; they do not hide values from visitors.
The publishable key is public by design, and the secret key must never be in the page. For local
development, `.env` is only a convenience for loading the public dashboard values.
